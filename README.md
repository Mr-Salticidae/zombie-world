# 僵尸危机：方块头 · 经典复刻版

一个 HTML5 Canvas 俯视角射击小游戏，致敬经典 Boxhead 玩法。单机客户端零构建，可直接部署到静态托管或上传至 B 站 toy 网页小游戏平台；2 人热点联机走 WebRTC 点对点、同样不需要服务器。

## 项目简介

玩家将在五张不同风格的俯视角战场中抵挡一波波僵尸和特殊敌人的进攻，通过连续击杀提升连击倍率，并逐步解锁更强武器。游戏内置键盘、鼠标和触屏操作，适合直接在浏览器中体验。

## 主要特性

- 单机客户端为纯前端实现（`index.html` + `style.css` + `script.js` + `multiplayer.js` + `p2p.js`），无需前端打包工具
- Canvas 渲染的俯视角动作射击玩法
- 独立地图选择页，五张地图均带实景缩略图卡片
- 美化主菜单，包含动态标题、特色徽章、氛围背景和僵尸剪影
- 菜单、暂停、结算、地图选择和操作说明界面
- 键盘经典模式、鼠标射击模式和移动端触屏摇杆（横屏竖屏都能玩）
- 9 种武器、5 张地图、5 级 BOSS、无双大招、3 档难度
- 接 Toy JS SDK 的排行榜：得分榜 / 坚守波数榜，总榜与本周榜（仅统计标准难度）
- 波次刷怪、连击倍率、武器解锁、掉落补给和爆炸连锁
- Web Audio 实时合成音效，无需额外音频资源

## 如何运行（本地开发）

`index.html` 通过相对路径引用 `style.css`、`multiplayer.js`、`p2p.js` 与 `script.js`，浏览器对 `file://` 直接打开有安全限制，建议起一个本地静态服务：

```bash
# 在项目根目录执行任意一种
python -m http.server 8000
# 或
npx serve .
```

然后浏览器访问 `http://localhost:8000/`。推荐使用 Chrome、Edge、Firefox 等现代浏览器。

## 2 人热点联机（不需要服务器）

> ⚠️ **代码已完成、测试已覆盖，但还没有在真机上跑通过一次。** 见下文《还没验证的那件事》。

主菜单的联机入口现在通向的是**热点直连**：两台手机连同一个热点，走 WebRTC DataChannel
点对点，全程不经过任何服务器。实现在 `p2p.js`，它把 `window.zombieNetwork` 换成了自己的实现
（WSS 那套原样留在 `window.zombieWsNetwork`）。

为什么是这个形态：

- 玩家几乎全在手机上，「租一台公网服务器」和「拿 PC 当主机」两条路都不成立
- 同一热点下两台设备在一个内网里，用 host 候选直接互连，**连 NAT 穿透都不用碰**——
  P2P 最常见的死法（对称 NAT 要 TURN 中转，而 TURN 就是一台要自己养的服务器）在这个场景下不存在
- **人数上限定死 2**：没有服务器就没有信令通道，offer/answer 只能靠人肉互发。
  两人一来一回两条码就够；四人星型要六次握手，那个 UX 不能用

怎么玩：一个人开热点（要开着自己的流量，不然游戏页面都打不开），另一个连上去，然后
一个点「我开房」出邀请码、另一个点「我加入」粘进去，客机再把应答码发回房主粘上，就连上了。
码走微信发或者当面扫都行。

实现上的几个取舍：

- **房主兼任服务器**：房间状态机（进房 / 准备 / 开局 / 结束 / 离开）就跑在房主页面里。
  这不是妥协——WSS 版的权威模拟本来也在房主浏览器里，而 `server/` 那千把行里绝大部分是在防
  一台面向陌生人的公共服务器（房间码、容量、限流、重连令牌、Origin 白名单），
  一条两台手机之间的直连管道上没有那些对手
- **码用无损压缩 + base64，不做 SDP 字段级压缩**。字段级压缩要靠模板重建，模板写错了表现是
  「码看着没问题但就是连不上」，在拿不到真机日志时这种 bug 最难查。无损方案体积大些
  （复制粘贴无所谓），但它不可能把连接搞坏。等要换二维码（装不下几百字节以上）再说
- **不配任何 iceServer**：同一热点下 host 候选就够，也不想为了联机去依赖外部服务
- **没有会话恢复**：一条 P2P 管道随页面而生随页面而灭，刷新就等于断线。
  `hasSavedSession()` 恒为 false——与其假装能恢复，不如直说
- `script.js` 一行没改传输相关的逻辑：`p2p.js` 对它呈现的方法、`room` 形状和 7 个事件
  （`room.state` / `match.start` / `input` / `snapshot` / `error` / `room.closed` / `status`）
  与 `ZombieNetwork` 完全一致

### 还没验证的那件事

**B 站 App 的 WebView 里，WebRTC 局域网直连到底通不通，至今没有真机结论。**
iOS 14 起访问局域网需要 App 持有 `NSLocalNetworkUsageDescription`，而这个权限属于 B 站 App、
不属于我们的页面；拿不到就只能退而求其次挂公共 STUN 走 NAT hairpin，那也不保证。

`test/p2p.test.js` 的 18 个用例覆盖了唯一新写的业务逻辑——房主那套房间状态机（进房、准备、
开局门槛、地图钳位、打完回大厅清准备、队友离开、双方 selfId 不能发混、单向性）以及码的编解码
往返。这些都是不碰 WebRTC 的部分，也正是没真机时最需要盯住的部分。**但传输层本身只能靠真机。**

### 真机验证：探针

`tools/webrtc-probe.html` 是为验证上面那件事写的一次性诊断页（单文件、零依赖、不进游戏包）。
它已作为 link-only 测试 Toy `20949059624960` 发到线上，**为的就是能在 B 站 App 里打开**；
本地跑用 `python -m http.server 8000` 开 `http://localhost:8000/tools/webrtc-probe.html`
（`localhost` 也是安全上下文，WebRTC 正常工作）。

探针分两步，**第一步一个人一台手机就能跑完**：

1. **单机自检**——本机开两个 `RTCPeerConnection` 自己连自己，不用第二台设备也不用开热点。
   它只问两件事：这个容器有没有 WebRTC、拿不拿得到 host 候选。自检过了不代表跨设备一定行
   （同机 loopback 不经过网络），但自检不过就一定不行，所以这是一道零成本的过滤，先跑它。
2. **跨设备实测**——两台手机连同一热点（开热点那台要出移动数据，否则页面都打不开），
   一台点「房主」一台点「客机」，邀请码 / 应答码用复制粘贴经微信互发。这一版**故意不做扫码**：
   要测的是网络能力不是扫码体验，少一个变量，失败时就少一个甩锅对象。

读结果只看「连线方式」一行：`host ↔ host` = 热点内直连、方案成立；`srflx` = 绕公网反射回来、
能用但依赖运营商 NAT 行为；`relay` = 必须中转服务器、方案不成立。

两个注意：页面必须从 **https**（或 localhost）打开；先用默认的**纯局域网**跑一次，连不上再勾
STUN 重跑一次，**两台手机模式必须一致**，两次结果合起来才说明问题。
「复制完整诊断报告」会把自检结论、候选类型、延迟、UA 和带时间戳的日志一并拷走。

探针还会顺手量出 SDP 精简后的字节数，用来判断下一版能不能把码换成二维码
（手机能稳拍清的二维码大约 300~500 字节）。

### WSS 版（冻结保留，2–4 人）

下面这套是给「哪天真有了公网服务器」准备的，`multiplayer.js` / `server/` / `test/server.test.js`
原样保留、29 个测试仍在跑。要切回去：把 `p2p.js` 末尾那两行换掉，让 `window.zombieNetwork`
指回 WSS 实例即可。它采用「WebSocket 房间服务器 + 房主权威模拟」：

- 2–4 人通过 6 位房间码加入，同一房间共享地图、敌人、波次、掉落和团队得分
- 客端只发送移动、瞄准、开火、武器和大招输入；房主推进战局并广播权威快照
- 10 秒断线重连窗口；队友倒地后，队伍撑到下一波即可复活
- 房主掉线超过窗口后房间关闭；当前版本不做房主迁移、公开匹配、聊天或长期战绩
- 单人模式不会发起网络请求，联机服务不可用也不影响原有单机玩法
- 当前权威模拟运行在房主浏览器；房主必须保持游戏页面在前台，否则浏览器后台节流会暂时冻结全房战局

联机开发与本地测试：

```bash
npm install
npm start
```

访问 `http://localhost:8080/`，打开 2–4 个浏览器窗口，使用同一房间码即可联调。
服务器同时托管静态客户端和 `/ws` WebSocket 端点；也可以将静态客户端部署到其他域名，
在联机大厅填写独立的 `wss://你的域名/ws`。

运行自动化测试：

```bash
npm test
node --check script.js
node --check multiplayer.js
node --check p2p.js
```

本地启动默认仅监听 `127.0.0.1`。生产环境至少应显式配置公网监听、HTTPS/WSS、
反向代理和 Origin 白名单：

```bash
HOST=0.0.0.0 ALLOWED_ORIGINS=https://你的游戏域名.example npm start
```

> B 站 Toy 包只包含静态客户端，`server/`、证书、环境变量和 `node_modules/` 不会打包进去。
> Toy 官方文档尚未明文承诺 WebSocket；公开发布前应先向 Toy 运营报备固定 WSS 域名、
> 传输字段和数据策略，取得书面确认，再完成 App 真机预览。

## Toy 平台能力（JS SDK）—— 查证记录 2026-08-07

结论先写在这：**Toy JS SDK 没有联机 / 实时同步 / 房间能力，不要再指望用它做多人对战。**

核查方式：从发布平台前端包（`//s1.hdslb.com/bfs/static/toy/app/publish/assets/index-*.js`）里取出
SDK 文档数据，并直接下载 SDK 本体 `//s1.hdslb.com/bfs/seed/toy/app/sdk/toy-sdk.js` 检索。
**SDK 版本 1.5.0，更新于 2026-07-31**，全部能力共 18 个：

| 分类 | API | B站 App | Web 端 |
|---|---|---|---|
| 容器 | `isSupport` `navigate` | ✅ | ✅ |
| 容器 | `saveImageToAlbum` `closeBrowser` | ✅ | — |
| 用户/作者 | `getUserProfile` `getAuthorProfile` `getAuthorVideos` `getAuthorRelation` `getVideoUserActions` | ✅ | ✅ |
| 云存储 | `setCloudStorage` `getCloudStorage` `removeCloudStorage` | ✅ | ✅ |
| 排行榜 | `submitScore` `getRankList` `getMyRank` | ✅ | ✅ |
| 媒体 | `requestCamera` `requestMicrophone` `stopMedia` | ✅ | ✅ |

在 `toy-sdk.js` 里精确检索：`websocket` / `createRoom` / `joinRoom` / `roomId` / `realtime` /
`multiplayer` / `matchmaking` **均为 0 次命中**。文件里出现 140 多次的 `room` 全部来自
`liveRoomHalf.*`（B站直播间 JSBridge，SDK 顺带打包的通用桥），与游戏联机无关；
唯一一处 `RTCPeerConnection` 是 SDK 与宿主容器通信的内部管道，不是对外能力。

要做「不用自建服务器的多人感」，方向是**排行榜 + 云存储**（异步竞争而非实时同框）：

- 排行榜按「toy + 榜位 + 周期」隔离；榜位固定 `1/2/3`（含义自定，如榜1 得分、榜2 波数）；
  周期 `all`（永久）/ `month` / `week` / `day`
- 分数为整数，范围 `-16777216 ~ 16777215`，允许 0 与负数；固定从高到低排序，
  同分先达成者靠前（先到先赢），名次唯一不并列
- **读榜游客可读**，上报分数需登录；判断是否上榜必须看返回的 `ranked` 字段，**不能用 `score` 判断**
- 云存储按「登录用户 + Toy」隔离，单个 Toy 最多 128 个 key-value，需登录但不触发用户数据确认
- 接入前一律先 `await toy.isSupport('xxx')` 判断，SDK 缺失/环境不支持时要能降级

文档入口：发布平台页内路由 `/sdk`（「开放能力」→ JS SDK / CLI / Skill 三个页签）。

## 排行榜

已接入，用的就是上面那套 SDK。设计取舍写在这里，免得后面看代码猜：

- **榜位**：`1` = 得分榜，`2` = 坚守波数榜，`3` 预留。**周期**只开了「总榜」`all` 与「本周」`week`。
- **只收标准难度**。轻松打得轻松、硬核敌人更多分自然更高，混进同一个榜这榜就废了；
  非标准难度的局在结算页明说「不计入排行榜」，不偷偷丢弃也不假装上传。
- **不擅自弹确认框**。首次上榜要由玩家点结算页的「上传成绩到排行榜」触发
  （平台会弹一次数据确认）；同意过一次后记在 `localStorage`，之后每局自动上传。
- 服务端只保留历史最高分，重复上报不会把成绩刷低，所以上传逻辑不用自己比大小。
- **读榜游客可读**，`getMyRank` 未登录会抛错——这属于正常路径，静默降级为不显示「我的排名」，
  不弹错误。判断是否上榜一律看 `ranked` 字段，不能用 `score`（分数允许为 0/负）。
- 榜单里的昵称是**别人可控的文本**，一律走 `textContent` 构建 DOM，不拼 `innerHTML`。
- **拿不到 SDK 的环境**（本地开发、站外托管、CDN 挂掉）：主菜单排行榜入口保持隐藏、
  结算页一个字都不提排行榜，游戏本体完全不受影响。

分数上限 16777215，本作实际到不了；上报前仍统一 `clampScore` 夹到 `0 ~ 16777215` 并取整。

## 操作方式

**电脑**

- 移动：`W` `A` `S` `D` 或方向键
- 射击：鼠标左键 / `空格` / `J`
- 切换武器：鼠标滚轮 / `Q` / `E` 或数字键 `1` 到 `9`（自动跳过没弹药的枪）
- 无双大招：`R`
- 暂停：`P` 或 `Esc`
- 鼠标模式：左键点击或按住朝指针方向攻击，右键点击或按住移动
- 瞄油桶：按住 `Shift`，枪口甩到最近的油桶
- 自动瞄准：默认开，主菜单/暂停页可关，见下方[自动瞄准](#自动瞄准)

**手机 / 平板**

- 移动：按住**屏幕左半边**拖动，就地生成摇杆
- 射击：按住**屏幕右半边**即开火——**按住不动会自动瞄最近的敌人**，拖动则决定射击方向（仍带小幅吸附）
- 切换武器：点右下角**换枪**键循环，或**直接点最下面那排武器格**指定一把。
  左半边是走位区，手指压在武器格上照样能拖着走，**只点一下不拖**才算换枪——
  竖屏时拇指本来就落在屏幕下沿，那正好压着武器栏，不这么分就成了「按下去只会换枪，人不动」
- 无双：右下角红色圆键 ｜ 暂停：左上角 `❚❚`
- 进入战斗时会浮一层操作说明，碰一下屏幕即消失
- **触屏诊断**（操作说明页最下面）：打开后画面左上角显示实时触点账目。
  只在排查手机 / WebView 上的触摸问题时用，默认关且不记进 localStorage，见下方[触屏输入](#触屏输入)

## 触屏输入

手机上的触摸不像看起来那么稳，尤其在 **App 内嵌的 WebView**（B 站 App 就是 WKWebView）里，
宿主自己有一层滚动视图，会跟页面抢手势。为此触屏那一段有三条铁律：

1. **用下标遍历 `TouchList`，不用 `for...of`**——迭代器不是每个 WebKit 都有，
   一旦抛错是整个触屏输入一起没，而手机上根本看不到那行报错
2. **属于游戏的触摸一律 `preventDefault`**（监听器因此必须 `passive:false`），
   CSS 那边 `touch-action:none` 也不只写在 `html/body`，游戏各层再各自声明一次。
   光靠 CSS 在 WKWebView 里不保险
3. **每个入口先对账**（`syncTouches`）：拿 `e.touches` 核一遍自己追踪的那两根手指还在不在，
   不在就当场放掉

第 3 条是「**iOS 端无法移动**」的正解。只靠 `touchend` / `touchcancel` 是不够的——
宿主可以把一整串触摸整个收走，结束事件一个都不发；那样 `tMove.id` 就永远停在一根
已经不存在的手指上，之后所有左半边的按下都被 `tMove.id === null` 这道门挡在外面。
右半边照常开火（走的是另一个槽），左半边彻底没反应，症状正是**能打不能走**。
对账让它在下一次触摸时自己恢复，不用重开页面。

### 诊断面板

这类问题在开发机上复现不出来，只能靠别人的真机——没有面板，回来的反馈只能是「就是动不了」。
打开后左上角显示实时触点账目，截一张图就够定位断在哪一环：

| 看到什么 | 说明断在哪 |
| --- | --- |
| `live` 一直是 0 | 触摸事件根本没进来，容器把手势整个吞了 |
| `start` 涨、`move` 不涨 | 拖动被宿主的滚动接管了 |
| `cancel` 在涨 | 手势被中途抢走，正是摇杆断的那一下 |
| `pd` < `claim` | `preventDefault` 没生效（事件不可取消），治不住抢手势 |
| `move id` 一直非空但 `vec` 不动 | 触点卡死了，对账那一步没兜住 |

## 自动瞄准

主菜单与暂停页都有开关（`自动瞄准：开 / 关`），**默认开**，选择记在 `localStorage`
（键 `zombie-world-aimassist`）。

起因是玩家反馈：**「瞄准的辐射范围有点窄，僵尸跟随后只能拉长距离后对冲射击」**。
根因不在准度而在朝向——键盘经典模式里 `朝向 = 移动方向`（见 `collectLocalInput`），
所以跟在屁股后面的僵尸物理上打不到，只能跑开、转身、再迎着它们冲，一局全是这个来回。

实现分两档，**只改「枪口朝哪儿」，不动伤害、射速、弹道**：

| 档 | 什么时候生效 | 行为 |
| --- | --- | --- |
| **硬锁定** | 没有明确瞄准输入时：键盘经典模式、手机按住右半边**不拖** | 枪口全向（360°）跟住范围内最近的敌人，于是**可以边后退边打身后**，对冲循环消失 |
| **软吸附** | 自己在瞄时：鼠标模式、拖动右摇杆 | 只在准星附近的锥角内修正（鼠标 ≈17°，触屏 ≈26°），方向仍然听玩家的；解决的是「擦着边过去」的空枪 |

### 瞄油桶

自动瞄准接管朝向之后，**手动引爆油桶这条玩法不能丢**，所以油桶单独有一套规则
（`pickAimTarget` 的 `barrelMode`）：

| 模式 | 什么时候 | 行为 |
| --- | --- | --- |
| `off` | 硬锁定的默认值 | 油桶**不进选靶池**——它不能把枪口从马上要咬到你的僵尸身上抢走 |
| `prefer` | 软吸附的默认值 | 油桶进池并带 `AIM_BARREL_PREF` = 0.72 的加权优势：准星压上去了就是明确意图 |
| `only` | **按住 `Shift`** | 只瞄油桶，敌人一概不看；范围内没桶就放手，等于临时把瞄准交还玩家 |

`prefer` 那档的理由是**油桶的价值恰恰在于旁边站着僵尸**——要是准星压在桶上还被旁边那只
吸走，这一枪的大爆炸就白瞄了。反过来，明确瞄着僵尸时旁边的桶也抢不走（见测试）。

`Shift` 这颗键主要是给**键盘经典模式**的：那个模式本来一点瞄准自由度都没有
（朝向 = 移动方向），不给个手动挡就真的只能等油桶被流弹打中。
手机端不需要额外按钮——**拖动右摇杆**指向油桶就走 `prefer` 那条路。
已经点着引信（`fuse`）的桶不锁，再补一枪是浪费。被锁的油桶括号是**橙色**，锁敌是黄色。

几条边界，都在 [test/aim.test.js](test/aim.test.js) 里锁住了：

- **锁定半径跟着武器走**（`WEAPONS[].aim`，按弹速 × 存活时间算的实际射程）：
  喷火器 150，霰弹枪 420，手枪 560，火箭筒 700。锁一个打不到的目标等于白烧子弹。
- **屏幕外一律不锁**，按**镜头矩形**判可见——贴地图边缘时镜头会被夹住，玩家并不在正中，
  不能用「以玩家为中心」去算。
- **贴脸的优先**：正面只有 12% 的距离加权（`AIM_BACK_BIAS`），够用来在几个等距目标里
  给个稳定偏好，但不会为了「面朝前」放过马上要咬到你的那只。
- **粘性**（`AIM_STICKY` = 1.22）：被围时不会在几只之间来回跳朝向；明显更近的新目标仍抢得过来。
- 被锁的敌人身上有**黄色直角括号**，玩家要能一眼看出枪口跟着谁。

### 「方向一换就乱打」——三处一起改

玩家反馈自动瞄准「方向一换就乱打了」。拆出来是三个各自独立的原因，缺一个都还是乱：

1. **打分基准用错了参照系。** 硬锁定原来拿「这一帧的移动方向」当基准算偏角，
   于是一按反方向键，所有目标的偏角权重整个翻面，锁着的那只被顶掉，枪口跳到另一只身上。
   改成拿**当前枪口朝向**做基准——等于让「我正打着谁」自己占一票，走位怎么变都不再洗牌。
   软吸附不动：那时候 `ax/ay` 是玩家真的在瞄的方向，本来就该听他的。
2. **换靶没有冷静期。** A 被 B 顶掉、B 又被 C 顶掉，一秒里枪口能甩三回。
   加 `AIM_HOLD` = 0.35 秒的冷静期，期间粘性从 1.22 提到 `AIM_STICKY_HOLD` = 2.2；
   贴脸的照样抢得过，小幅更近的抢不走。
3. **转向是瞬移。** 换靶那一帧朝向直接跳过去，中途打出的子弹这一发朝左下一发朝右。
   加 `AIM_TURN` = 13 rad/s 的角速度上限，180° 要转 15 帧（约 0.25 秒），
   打出去的是**扫过去**的一串。

外加一条：**被石柱挡住的目标不进选靶**（`losBlocked`）。原来会锁一个打不到的目标，
子弹全打在柱子上——一边被咬一边对着石头开枪，这是「乱打」里最气人的一种。
而且僵尸最爱堵在柱子后头，跟下面的寻路 bug 正好互相喂。
判挡用 `blockingPillar`（对圆是解析解，每个目标只 `O(柱子数)`）而不是 `losBlocked` 的采样射线，
便宜到可以把整个候选池都验一遍——不会出现「前几名全被挡、后面明明有能打的」。
半径传 0，跟子弹自己的判定（`hitPillar(b.x, b.y, 0)`）对齐。全被挡就干脆不锁，把朝向还给玩家。

联机下自动瞄准算在**本机**的 `collectLocalInput` 里，修正后的 `ax/ay` 随输入发给房主，
房主的权威射击用的就是这个方向；`aimLock` 是对象引用，`copyScalars` 会自动把它挡在快照外。

开关关掉后一切回到原样：朝向重新等于移动方向（键盘）/ 指针方向（鼠标），括号也不再画。

## 僵尸绕障

反馈：**僵尸卡在墙体（石柱）后面过不来**，玩家往柱子后一站就能无限安全收割。

老做法是「距离没拉近就往侧面推一个分量」，两处都不对：

- **判据错**：拿的是「跟玩家的距离有没有拉近」。玩家绕着圈跑，明明在走的僵尸被判成卡住；
  玩家迎面走过来，真卡死的僵尸反而一直判成正常
- **绕不完**：侧向分量封顶 1.15，最多偏 49°，而且每 2 秒强制换一次边。
  绕过一根 `r=64` 的柱子要走 3 秒以上——**换边比绕完还快**，于是永远绕不出去，
  僵尸就在柱背面来回蹭

现在两处都换掉：

- **判据换成「自己这半秒真的挪了多远」**（`z.px/z.py`），跟玩家怎么动完全无关。
  已经贴上去开咬的不算卡住——它就该站着不动，判成卡住会让它顺手把玩家脚边的油桶点了
- **绕行换成切线**（`blockingPillar`）：找出挡在自己与玩家之间、离自己最近的那根柱子，
  直接朝「刚好擦过柱边」的方向走。**边一旦选定就守住**，直到线真的通了才松开；
  第一次被挡时往玩家所在的那一侧绕，路更短
- `collide` 从单轮松弛改成**两轮**：单轮是「推出 A 的同时被推进 B」，
  在成对石柱之间那条约 37px 的窄缝里会左右弹一辈子，看着就是卡在墙里出不来

判定半径统一用「柱子 + 自己 + 4px 余量」，绕行和「路通了没有」共用同一个判断，
免得走的时候按 A 标准、判断的时候按 B 标准。

实测（把玩家钉在最大那根柱子 `r=64` 正后方，量每只僵尸第一次摸到玩家用了多久）：

| 场景 | 改前 中位 / 最慢 | 改后 中位 / 最慢 |
| --- | --- | --- |
| 1 只，玩家不动 | 6.9s / 6.9s | **3.3s / 3.3s** |
| 1 只，玩家左右挪 | 9.4s / 9.4s | **2.7s / 2.7s** |
| 10 只，玩家不动 | 6.8s / 10.5s | **4.1s / 9.3s** |
| 10 只，玩家左右挪 | 7.3s / 9.5s | **4.0s / 8.4s** |
| 8 只穿窄缝 | 6.0s / 7.3s | **5.7s / 6.9s** |

两版都没有「永远到不了」的个体，但改前那种「在柱背面来回蹭好几秒」的观感正是
玩家说的「过不来」；切线绕行把它砍掉一半以上，而且不再左右摇摆。
`blockingPillar` 的边界（谁算挡路、两根都挡时取哪根、擦边算不算）在
[test/aim.test.js](test/aim.test.js) 里锁住了。

## 自动切枪

反馈：**偶尔会自己切枪，没能复现**。查下来是两条路径，都不是随机的：

1. **解锁新武器时无条件 `p.weapon = i`。** 正打着加特林的人会在某次击杀之后突然变成拿手雷——
   没按任何键，横幅也不一定看得见。现在只在**手上这把已经用不了（空弹匣）或还是开局那把手枪**
   时才自动装上；其余情况只报解锁，枪留在手里，横幅改成「点武器栏切换」
2. **弹药打空自动换手枪**，而且一声不吭。这条得留着（总得换一把），
   但加了一条横幅说明是哪把打空了，不再像「枪自己乱切」

## 货币系统

还没做。约束、两条可选路线（局内货币 / 存档货币）和动手前要先定的三件事，
记在 [docs/currency-design-note.md](docs/currency-design-note.md)。
一句话结论：**先做局内货币且只卖消耗品**——不碰存档、不碰排行榜公平性，
也不跟「连击解锁武器」这条核心成长线抢位置。

## 多设备适配

参照官方《Toy 多设备自适应设计参考》（见 [docs/toy-responsive-guide.md](docs/toy-responsive-guide.md)）做了手机 / 平板 / PC 三档适配：

- **画布等比缩放**：逻辑用虚拟坐标，渲染时按容器尺寸映射真实像素，不写死宽高。
- **按物理像素出图**（2K/4K 屏发糊的根因）：画布后备缓冲区曾经恒为 `VW×VH` 个像素，
  却被 CSS 拉伸到整块屏幕——2K 屏上等于把 960 宽的位图放大 2.25 倍，再叠 `devicePixelRatio`，
  屏越大越糊。现在后备缓冲区按 **CSS 尺寸 × dpr** 出真实物理像素，
  绘制坐标仍走虚拟坐标系（`ctx.setTransform` 负责换算），游戏逻辑一行没改。
  预渲染的地面大图跟着升清，步进 `1 / 1.5 / 2`（2× 时 3840×2560 约 39MB，手机封顶 1.5×），
  跨档才重建，拖窗口不会反复重画。
- **横竖屏都能玩**：横屏（含 PC）用经典 `960×640` 视口；**竖屏换成等面积的竖版视口**（如 `581×1057`），
  可视面积保持 61 万像素不变，竖着玩不会因为看得少而变难。竖屏只弹一条可关掉的提示横幅，
  **不再冻结游戏**——B站 App 内嵌 WebView 常常锁竖屏，转不过来的人以前是直接玩不了。
- **安全区**：`viewport-fit=cover` + `env(safe-area-inset-*)`，画布与界面避开刘海、底部指示条。
- **移动端可视区**：用 `100dvh` 处理地址栏展开收起；监听 `resize` / `orientationchange` / `visualViewport` 重算画布。
- **输入分层**：`pointer:coarse` 判定触摸设备显示虚拟摇杆，PC（鼠标/键盘）隐藏摇杆；三套输入共用一套游戏逻辑。
- **触屏按钮按画布实位摆放**：换枪 / 无双 / 暂停由 JS 依 `getBoundingClientRect` 定位，
  保证压不到底部武器栏，也不会掉进刘海或圆角。
- **性能**：手机端自动降低粒子数量与爆炸碎屑上限，缓解低端机卡顿。

可在浏览器开发者工具的设备模拟下，分别检查手机竖/横屏、平板、PC 表现。

## 画质（分辨率倍率）

主菜单可切三档，选择记在 `localStorage`；按钮上会显示当前实际倍率（如「画质：自动（2.3×）」），

| 档位 | 渲染倍率上限 | 说明 |
| --- | --- | --- |

## 难度

主菜单可切三档，选择记在 `localStorage`：

| 档位 | 敌人数量 | 敌人血量 | 受到伤害 | BOSS 血量 |
|---|---|---|---|---|
| 轻松 | ×0.75 | ×0.8 | ×0.7 | ×0.72 |
| 标准 | ×1 | ×1 | ×1 | ×1 |
| 硬核 | ×1.3 | ×1.3 | ×1.35 | ×1.45 |

BOSS 排布：第 1–5 波五级递进，**第 6 波起在前四级之间轮转**并逐波变强，
**每逢 5 的倍数波**僵尸博士登场。第 5 波之后不再是每波都打满技能博士。
