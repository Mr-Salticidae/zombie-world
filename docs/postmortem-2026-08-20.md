## 二、几次方向被推翻（本次复盘的重点）

### 1. 「没有公网服务器」——一个错误前提裁掉了两个月的方案空间 ❗

README 和项目记忆里长期写着「租一台公网服务器不成立」，于是所有联机设计都在
「怎么不用服务器」这个约束下打转：人肉互发 SDP、二维码压缩、Cloudflare 免费信令……

SSH 上去之后发现：**服务器 2026-07-28 就部署好了，`zombie-world.service` 已经连续跑了 23 天。**
当初只配了 `listen 80` + `server_name 43.128.2.172`（纯 IP、纯 HTTP），
而 https 的 Toy 页面连不了 `ws://`（混合内容）——所以它是个**连不上的空壳**。
缺的从来不是服务器，是域名和证书。

**这是本轮代价最大的一次误判。** 而且它不是"信息不足"，是"有信息但没去看"——
一条 SSH 就能查清的事实，被一句写在文档里的结论挡了两个月。

### 2. 「iOS 本地网络权限死结」——我复述了一个已被推翻的猜想 ❗

我在会话中把「iOS 访问局域网要 App 持有 `NSLocalNetworkUsageDescription`，
而权限属于 B站 App」当作未解风险讲了一遍，还据此写进了 STUN 的代码注释。

实际上 2026-08-12 的真机测试**已经排除了这个猜想**（权限是正常的），
真正卡住的是网卡/路由层：浏览器只沿默认路由那张网卡采集 ICE 候选，
而手机开热点时默认路由不走热点网卡。这条结论就写在项目记忆里，我没先读就下了判断。

### 3. Cloudflare 信令——完整做完，整套没上线（沉没成本）

按「零成本零维护」的约束，设计并实现了 Worker + Durable Object 信令服务：
纯逻辑与平台解耦、22 条单测、本地两标签页端到端跑通、部署文档齐全。

最后一步卡死：`dash.cloudflare.com` 对命令行客户端返回 bot 挑战页
（`Just a moment...`，Ray ID `-SIN`），而 wrangler 的 OAuth 必须去那里换 token。
试了 4 次、换了 3 种方式（含用浏览器扩展点授权）都不可能成功。

**没有白费的部分**：`signal/room.js` 是纯逻辑，22 条测试仍在跑；
`dev-server.js` 是可执行的接口说明。**白费的部分**：Worker 适配层、wrangler 部署包、
以及排查 OAuth 那一个多小时。

### 4. 「Minecraft 式局域网发现」——正确设限，不算推翻

用户要的观感在浏览器里做不到（无 UDP / 组播 / 监听端口，页面当不了服务器）。
这一条第一时间就说清楚了，并把问题拆成「发现 / 信令 / 传输」三格，
指出只有中间那格能改。**这次是对的**，值得保留为模式。

## 三、方法论沉淀

### 文档里的结论会过期，而过期结论会裁掉方案空间 ⭐⭐

**核心**：写在 README / 记忆里的"约束"，用久了会被当成物理定律，
但它可能只是某一天的观察，甚至可能当时就写错了。

**来源**：本轮第 1 条（「没有服务器」，实际有）与第 2 条（「iOS 权限死结」，实际已排除）。

**验证状态**：⭐⭐ 二次验证——同一轮里独立出现了两次，且都指向"未复核的旧结论"。

**操作规则**：
1. 当一条文档结论正在**否决一整类方案**时，先花 5 分钟复核它，再接受它
2. 复核成本越低、结论影响越大，越要先复核（SSH 一条命令 vs 两个月的绕路）
3. 结论写进文档时带上**日期和验证方式**，让后来者知道它有多旧、多硬

**反例/边界**：不适用于低影响的细节结论——为每条注释做复核会瘫痪掉正常工作。
门槛是"它是否在否决一个方向"。

### 动手前先读项目记忆，尤其是"已被推翻的猜想"那一栏 ⭐⭐

**核心**：项目记忆里最有价值的不是"已知的事"，是"已经排除掉的猜想"——
因为那些猜想通常听起来很合理，会被反复重新提出。

**来源**：本轮第 2 条。iOS 权限那个猜想我复述得很自然，因为它确实合理。

**验证状态**：⭐⭐ 二次验证——2026-08-12 那次已经推翻过三个"合理猜想"，这次又中一个。

**操作规则**：
1. 记忆文件里单开一栏「已排除的猜想」，写清楚**怎么排除的**
2. 会话开始就读，不要等到踩到了才回头翻
3. 复述一个风险之前，先确认它不在那一栏里

### 平台的免费层要验证到"最后一公里" ⚠️

**核心**：免费层的额度、能力都可以提前查清，但**能不能完成认证/部署**只有真跑才知道。
Cloudflare 的容量和定价我查得很准，栽在了登录上。

**来源**：本轮第 3 条。

**验证状态**：⚠️ 初次发现——只有这一个案例，不排除是本机代理环境的特例。

**操作规则**：
1. 选定平台后，**第一件事是跑通一次最小部署**（hello world），再开始写业务代码
2. 尤其当运行环境有代理 / 在特殊网络区域时

**反例/边界**：如果部署链路本来就熟（比如用户已有的服务器），这条不适用。

### 把用户的字面要求拆成「能做的」和「做不到的」，分开答复 ⭐

**核心**：用户说"做成 Minecraft 那样"时，真正的诉求往往是其中一部分。
把功能拆成几格、逐格标注可行性，比笼统地说"做不到"或硬着头皮做都好。

**来源**：本轮第 4 条——拆成"发现 / 信令 / 传输"三格之后，
双方很快就在"只能改中间那格"上达成一致。

**验证状态**：⭐ 初次发现（本项目内）。

**操作规则**：
1. 先给出**能力边界的物理原因**（浏览器没有 UDP），不是"做起来很难"
2. 再把目标拆格，逐格标 ✅/❌/⚠️
3. 让用户在"能改的那几格"里做选择

### 砍数据结构之前，先把"谁会读它"一个字段一个字段列出来 ⭐

**核心**：快照瘦身砍掉 64%，靠的不是猜，是照着渲染函数和客机本地逻辑
把字段来源逐个对出来，并在代码里注明出处。

**来源**：`NET_SPEC` 的白名单。砍漏一个字段的表现是"房主看得见客机看不见"，极难查。

**验证状态**：⭐ 初次发现。

**操作规则**：
1. 白名单而不是黑名单
2. 每组字段注明"谁在读它"
3. 砍完必须端到端实跑对账（数量、得分、抽样字段精度）
